**Step 2: Create `src/common/health/rabbitmq.health.ts`** (new file)

Create a custom HealthIndicator that probes RabbitMQ connectivity via amqplib:

```typescript
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { HealthCheckError, HealthIndicator, HealthIndicatorResult } from '@nestjs/terminus';
import * as amqp from 'amqplib';
import { AppConfig } from '../../config/app.config.js';

@Injectable()
export class RabbitMQHealthIndicator extends HealthIndicator {
  constructor(private readonly configService: ConfigService) {
    super();
  }

  async isHealthy(key: string): Promise<HealthIndicatorResult> {
    let connection: amqp.Connection | null = null;
    try {
      const { rabbitmq } = this.configService.getOrThrow<AppConfig>('app');
      connection = await amqp.connect(rabbitmq.url);
      await connection.close();
      connection = null;
      return this.getStatus(key, true);
    } catch (error) {
      const message = error instanceof Error ? error.message : String(error);
      throw new HealthCheckError(
        'RabbitMQ health check failed',
        this.getStatus(key, false, { message }),
      );
    } finally {
      if (connection) {
        try { await connection.close(); } catch { /* ignore close error */ }
      }
    }
  }
}
```

Key points:
- Uses `configService.getOrThrow<AppConfig>('app')` then `.rabbitmq.url` (matching existing config pattern in app.config.ts)
- Opens a throwaway amqplib connection, closes it immediately
- `finally` block defensively closes connection if error occurred after connect but before close
- Sets `connection = null` after successful close to prevent double-close in `finally`

Per D-05 and DEPLOY-01: Add a `healthcheck:` block to the `api` service in `compose.yml`.

Add the following block to the `api` service definition, after the `restart: unless-stopped` line and before the `ports:` line:

```yaml
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://localhost:3000/health || exit 1"]
      interval: 15s
      timeout: 10s
      retries: 5
      start_period: 30s
```

IMPORTANT per research: Use `wget` NOT `curl` — `node:22-alpine` has wget but NOT curl.

Tuning rationale:
- `interval: 15s` — frequent enough without hammering the endpoint
- `timeout: 10s` — allows for DB/RabbitMQ probe latency
- `retries: 5` — 5 failures x 15s = 75s before marking unhealthy
- `start_period: 30s` — grace period while NestJS bootstraps and TypeORM initializes

The `api` service already has `depends_on: postgres: condition: service_healthy` and `rabbitmq: condition: service_healthy`, so it only starts after those services are healthy. The API healthcheck then validates the app itself is ready.

Do NOT change the `admin-ui` service — it has no health endpoint (it serves static files via nginx, HTTP 200 on root is sufficient, checked by CI in Plan 02).

Verify all existing services (postgres, rabbitmq) still have their healthchecks intact. Do not modify them.
